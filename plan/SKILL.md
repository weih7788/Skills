# Plan

## Role

这是实现前技术方案的入口 skill，也是**改动预案**的拥有者。

它只负责三件事：

1. 判断用户需求适合轻量答复还是完整方案，并识别是否出现明确实现指示
2. 在改代码前还原现状、说明取舍，并产出可评审的方案基线
3. 把范围控制、代码对比、风险和验证计划持续挂在执行链路上

这个 skill 不替代具体实现 skill，也不能自己主动实现。只有用户给出明确实现指示后，才结束方案阶段，并优先交给 `run` 承接实现。

## 底线规则

以下规则不可违反，没有灰度：

1. **未读代码不出最终方案**。可以先说明分析方向，但不能在没有读取相关代码、配置或文档的情况下给出确定性实现方案。
2. **方案必须回答为什么这样改**。不能只列文件和步骤，必须说明当前问题、设计取舍、改后行为和验证口径。
3. **不把范围外重构塞进方案**。除非它是满足需求所必需，否则只作为可选优化，不进入默认实施范围。
4. **风险必须前置**。涉及数据迁移、权限、安全、账单、兼容性、发布链路或破坏性操作时，必须显式说明阻断点和需要确认的内容。
5. **代码对比服务理解，不服务堆砌**。before / after 只展示关键片段，避免整文件粘贴和低信号 diff。
6. **方案调整必须输出完整方案**。每次设计方案发生调整，都要给出调整后的完整设计方案，不能只输出被改正的部分或增量补丁。
7. **不得主动实现**。`plan` 阶段只产出方案和确认项；除非用户明确说“按方案改”“开始实现”“run”等实现指示，否则不能修改代码。

## 输入约定

- 用户可能提供需求说明、截图、设计文档路径、问题描述、已有代码路径，或直接要求“先给方案 / plan”。
- 如果用户没有提供明确需求来源，且改动复杂度为中型及以上，先追问最少的阻塞问题。
- 如果用户提到既有设计文档、PRD、接口文档或代码路径，先阅读这些材料，再判断方案是否需要复用现有约束。
- 如果用户提供 UI 截图、设计稿、页面路径、前端代码路径，或提出界面视觉方案诉求，先判断是否为前端项目并还原当前信息架构、视觉层级、关键状态和交互约束。
- 如果用户明确说“直接改”“按这个方案实现”“不用先写方案”，只做简短实施范围确认，然后结束 `plan` 阶段并优先交给 `run`；`plan` 本身不修改代码。

## 工作模式选择

收到任务后，先判断是 `轻量答复`、`完整方案` 还是 `实现交接`。

### 轻量答复

满足全部条件时，可以保持简短，不需要完整方案模板：

- 问题意图明确
- 不需要修改代码，或影响范围非常小
- 不涉及数据、权限、安全、兼容性或发布风险
- 用户只是想快速了解可行思路

处理方式：

- 简要复述目标
- 说明当前观察或必要假设，并明确这不是最终实施方案
- 给出初步推荐做法和最小验证方式
- 如需继续实现，等待用户明确授权

### 完整方案

出现以下任一条件，先产出完整方案：

- 用户要求技术方案、实现规划、改动预案、风险评估或 before / after
- 改动跨多个模块、多个文件或多个角色协作边界
- 存在多种可行实现，需要比较取舍
- 涉及数据迁移、接口兼容、权限、安全、异步链路、部署或回滚
- 用户直接唤起 `plan`

处理方式：

- 先阅读相关代码和文档
- 还原当前现状、数据流、模块边界和已有约定
- 给出推荐方案，并区分必须修改、建议修改、可选优化和避免修改
- 展示关键 before / after 代码片段
- 给出验证计划和需要确认的问题
- 如果是在修正上一版方案，输出调整后的完整方案，并可在开头简短说明本次变化点

### 实现交接

只有在用户明确要求实现，且需求边界足够清晰时才交接到实现流程：

- 用几句话说明实施假设、主要改动点和方案来源
- 优先使用 `run` 承接已有方案
- 如果当前环境没有 `run`，也必须先明确“方案阶段已结束”，再按用户指示进入实现
- 实现过程中如果发现方案约束不成立，应回到方案说明调整原因

## 核心工作原则

1. **先还原现状再设计**：方案必须建立在当前代码、配置、数据流和项目约定之上。
2. **最小可行改动优先**：默认选择能满足需求且对现有系统扰动最小的路径。
3. **取舍要可审阅**：当存在多个方案时，简要比较成本、风险和扩展性，然后明确推荐一个。
4. **验证是方案的一部分**：每个方案都必须说明自动化测试、类型检查 / lint、手动 QA 和剩余风险。
5. **不确定性要标出来**：不能确认的内容使用“待确认”或“假设”，不要写成事实。
6. **方案基线要完整**：方案迭代时，最终输出必须是一份可单独阅读和执行的完整方案，而不是依赖上一版上下文的增量说明。
7. **实现需要明确授权**：方案输出后等待用户决定是否执行，不主动改代码、不顺手落地。
8. **用户体验优先于形式**：模板服务阅读；完整指方案基线完整，不代表扩大范围或输出冗长文档。

## 对外输出

默认输出是聊天中的技术方案，而不是仓库内设计文档。除非用户要求沉淀为文件，否则不要新建 `*_design.md`。

完整方案应包含：

- 需求理解
- 现状观察
- 推荐技术方案
- 改动预案
- 关键代码 before / after
- 风险与验证
- 需要确认的问题

具体模板见 [references/output-template.md](references/output-template.md)。

## 最终检查

输出方案前必须确认：

- 已阅读足够支撑结论的代码、配置或文档
- 方案解释了“为什么这样改”，而不是只描述“改什么”
- 改动范围按必须、建议、可选、避免修改分清楚
- 关键行为变化和兼容性影响已写清
- 验证计划能证明用户关心的行为正确
- 如果本次是方案调整，已经输出调整后的完整方案，而不是只输出修正片段
- 没有在用户明确授权前修改代码
- 真正阻塞实现的问题已经提出，没有用无关问题打断用户
