# Output Template

## 完整方案模板

默认使用以下结构。小需求可以压缩每个章节的篇幅，复杂需求可以扩展，但完整方案不能省略风险和验证。

如果本次是在调整上一版方案，可以先用 1-3 条列出“本次变化点”，但随后必须输出调整后的完整方案。不要只输出改正的部分，也不要让读者必须回看上一版才能执行。

```markdown
**本次变化点**（仅方案调整时需要）
- 调整了……
- 移除了……

**需求理解**
用一小段说明产品目标、成功标准和已知边界。

**现状观察**
列出相关文件、当前逻辑、实际调用链、数据流、模块边界和重要约束。跨入口任务应标明每个入口汇入哪个共用方法。

**技术方案**
给出推荐方案，并说明为什么它适合当前代码库。如果存在多个可行方案，简要对比后明确推荐一个。

**改动预案**
- `path/to/file-a.ts`：改什么，为什么改
- `path/to/file-b.ts`：改什么，为什么改

**代码对比预览**
按文件展示关键 before / after 片段，只展示理解改动所需的代码。跨入口或跨方法时，先列出入口到副作用的调用链，再展示调用方改在何处、如何调用新增或修改的方法，以及被调用方法的关键实现。
如果方案新增方法、函数、变量、字段、常量、类型或其他代码符号，必须在对应文件的对比中展示其名称、声明位置和关键定义，不能只写“新增某方法 / 变量”。

**风险与验证**
说明潜在风险、兼容性影响、需要运行的测试和手动验证步骤。

**需要确认**
只提出真正阻塞实现的问题。如果没有阻塞项，说明方案已具备实现条件，并等待用户明确指示是否交给 `run` 或其他实现流程。
```

## 代码对比格式

每个文件建议使用下面的格式：

````markdown
### `path/to/file.ts`

修改原因：
说明为什么需要改这个文件。

修改前：

```ts
// 当前相关代码
```

修改后：

```ts
// 建议修改后的代码
```

影响：
说明改动后行为会发生什么变化。
````

### 跨入口或跨方法的调用链

当一个方案复用共用服务、增加清理步骤或改变写入顺序时，在代码对比前用一行链路标明真实调用关系，例如 `HTTP 入口 A / B → Manager → importRowsForAccounts → 清理旧映射 → importRows → 数据库`。链路中的每一段应能在已读源码中找到；若某段是建议新增，标注“拟新增”。

对应的 before / after 至少回答三个问题：

1. **谁调用**：展示入口或上层方法实际调用哪个共用方法。多个入口汇入同一方法时，可用现有调用片段加一行文字证明，无需复制相同代码。
2. **何时调用**：展示修改后的调用点及前后顺序，包括校验、清理、写入、事务与结果统计中与需求相关的步骤。
3. **调用后做什么**：展示新增或修改方法的关键查询条件、匹配、写入/删除分支及返回值如何被调用方使用。不要以 `// 查询并删除`、`// 原有逻辑` 或空方法体代替决定行为的代码；仍可省略与本次行为无关的细节，并标注为示意代码。

例如，若 `importSearch` 和 `importExcel` 已共同调用 `importRowsForAccounts`，应先说明这两个现有入口，再对比该共用方法的实际调用顺序：修改前直接循环 `importRows`；修改后先计算有效身份、调用 `removePreviousMappings`、再循环 `importRows`，最后用清理前的存量计算结果。随后展示 `removePreviousMappings` 如何限定租户/船司、按身份筛选、删除映射以及只清理无剩余映射的名称。只贴循环与两个新增方法签名，无法让读者看出调用链或副作用，不符合此格式。

### 新增方法、变量或其他代码符号

当设计包含新增代码符号时，沿用上述文件级格式，并按以下规则补充：

- `修改前`：展示新增符号计划插入位置附近的现有代码；如果上下文没有展示价值，明确写注释 `// 当前不存在该方法 / 变量`。
- `修改后`：展示新增方法的完整签名、返回类型和关键分支，或新增变量 / 字段 / 常量的名称、类型、初值及所属作用域。
- `影响`：说明新增符号由谁调用或读取、生命周期 / 可见范围，以及它如何改变现有行为。
- 同一文件新增多个紧密相关的符号时可以合并展示；无关符号应拆分，避免读者无法对应设计意图。

示例：

````markdown
### `path/to/service.ts`

修改原因：
抽取统一的状态判断，并缓存允许重试的最大次数。

修改前：

```ts
export class TaskService {
  // 当前不存在 canRetry 方法和 maxRetryCount 字段
}
```

修改后：

```ts
export class TaskService {
  private readonly maxRetryCount = 3;

  private canRetry(retryCount: number): boolean {
    return retryCount < this.maxRetryCount;
  }
}
```

影响：
`executeTask` 将调用 `canRetry` 判断是否继续重试；`maxRetryCount` 仅在 `TaskService` 实例内部可见。
````

## 复杂度分级

小改动的方案保持简短：

- 需求理解
- 涉及文件
- 关键 before / after
- 验证方式

中等改动需要补充：

- 当前数据流
- 实现顺序
- 风险和回退说明
- 重点测试

大型改动需要补充：

- 分阶段实现方案
- 数据迁移或兼容策略
- 测试矩阵
- 发布、灰度或回滚建议

## 方案调整要求

每次设计方案发生调整，都必须重新输出一份完整方案：

- 可以保留一个很短的“本次变化点”帮助用户快速定位差异。
- 完整方案本体必须包含调整后的需求理解、现状观察、技术方案、改动预案、代码对比、风险与验证。
- 完整指“方案可单独阅读和执行”，不代表扩大本次实施范围。
- 不要只回复“把 A 改成 B”或只给局部段落。
- 不要依赖“其余同上”作为方案主体；最终文本应能被 `run` 直接承接执行。

## 验证计划

验证计划应包含：

- 需要运行的自动化测试。
- 相关类型检查或 lint。
- 用户可见行为的手动 QA 步骤。
- 边界场景。
- 如果本地无法完整验证，需要说明剩余风险。
