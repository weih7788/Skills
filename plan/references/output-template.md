# Output Template

## 完整方案模板

默认使用以下结构。小需求可以压缩每个章节的篇幅，复杂需求可以扩展，但完整方案不能省略风险和验证。

如果本次是在调整上一版方案，可以先用 1-3 条列出“本次变化点”，但随后必须输出调整后的完整方案。不要只输出改正的部分，也不要让读者必须回看上一版才能执行。

```markdown
**本次变化点**（仅方案调整时需要）
- 调整了……
- 移除了……

**需求理解**
用一小段说明产品目标、成功标准和已知边界。

**现状观察**
列出相关文件、当前逻辑、数据流、模块边界和重要约束。

**技术方案**
给出推荐方案，并说明为什么它适合当前代码库。如果存在多个可行方案，简要对比后明确推荐一个。

**改动预案**
- `path/to/file-a.ts`：改什么，为什么改
- `path/to/file-b.ts`：改什么，为什么改

**代码对比预览**
按文件展示关键 before / after 片段，只展示理解改动所需的代码。

**UI 设计效果图**（前端样式 / 布局 / 视觉调整，或 UI 设计图类诉求需要）
展示一张照片风格或截图风格的位图 UI 效果图，并简要说明它覆盖的页面、状态、响应式范围和关键视觉取舍。只要判断为前端项目且方案涉及样式、布局、组件视觉或交互状态调整，就必须包含本节；不能只用 Mermaid、ASCII、纯文字、抽象流程图或线框结构图替代。

**风险与验证**
说明潜在风险、兼容性影响、需要运行的测试和手动验证步骤。

**需要确认**
只提出真正阻塞实现的问题。如果没有阻塞项，说明方案已具备实现条件，并等待用户明确指示是否交给 `run` 或其他实现流程。
```

## 代码对比格式

每个文件建议使用下面的格式：

````markdown
### `path/to/file.ts`

修改原因：
说明为什么需要改这个文件。

修改前：

```ts
// 当前相关代码
```

修改后：

```ts
// 建议修改后的代码
```

影响：
说明改动后行为会发生什么变化。
````

## 复杂度分级

小改动的方案保持简短：

- 需求理解
- 涉及文件
- 关键 before / after
- 验证方式

中等改动需要补充：

- 当前数据流
- 实现顺序
- UI 设计效果图（如果是前端项目并涉及样式、布局、组件视觉或交互状态调整，或涉及设计稿调整；必须是一张照片风格或截图风格的位图图片）
- 风险和回退说明
- 重点测试

大型改动需要补充：

- 分阶段实现方案
- 多状态或多断点 UI 效果图（如果前端样式调整涉及复杂页面、多端适配或关键交互状态；每张都必须是照片风格或截图风格的位图图片）
- 数据迁移或兼容策略
- 测试矩阵
- 发布、灰度或回滚建议

## 方案调整要求

每次设计方案发生调整，都必须重新输出一份完整方案：

- 可以保留一个很短的“本次变化点”帮助用户快速定位差异。
- 完整方案本体必须包含调整后的需求理解、现状观察、技术方案、改动预案、代码对比、风险与验证。
- 完整指“方案可单独阅读和执行”，不代表扩大本次实施范围。
- 不要只回复“把 A 改成 B”或只给局部段落。
- 不要依赖“其余同上”作为方案主体；最终文本应能被 `run` 直接承接执行。

## 验证计划

验证计划应包含：

- 需要运行的自动化测试。
- 相关类型检查或 lint。
- 用户可见行为的手动 QA 步骤。
- 边界场景。
- 如果本地无法完整验证，需要说明剩余风险。
