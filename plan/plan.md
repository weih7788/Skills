# Plan

## 目标

帮助用户把产品需求转化为清晰、可执行、可评审的技术方案。

在真正修改代码之前，先说明：

- 需求目标是什么
- 当前代码如何工作
- 推荐采用什么技术方案
- 需要改哪些文件
- 为什么要这样改
- 改完后行为会有什么变化
- 如何验证改动是正确的

这个 skill 的重点不是立刻写代码，而是先让用户看清楚实现路径、影响范围和风险，再决定是否继续实施。

## 使用场景

当用户提出以下需求时，使用本 skill：

- 需要实现一个产品需求
- 需要先给技术方案
- 需要先分析代码再决定怎么改
- 需要代码改动预案
- 需要重构方案
- 需要架构或数据流设计建议
- 需要改前 / 改后代码对比
- 需要实现前风险评估
- 用户直接唤起 `plan`

## 核心流程

1. 简要复述需求目标和预期产品结果。
2. 先阅读相关代码，不要凭空设计方案。
3. 梳理当前架构、数据流、模块边界、已有约定和测试方式。
4. 给出满足需求的最小可行实现方案。
5. 区分必须修改、建议修改、可选优化和不建议修改的内容。
6. 在改代码前，先展示：
   - 要修改的文件
   - 每个文件的修改原因
   - 修改后的行为变化
   - 关键代码的 before / after 对比
   - 测试和验证计划
7. 除非用户明确要求“直接实现”“按方案改”“继续修改”，否则不要直接改代码。

## 输出格式

默认使用中文输出。内容要清晰、克制、便于扫读。根据需求复杂度调整长度，不要为了形式输出过长文档。

建议使用以下结构：

```markdown
**需求理解**
用一小段说明产品目标、成功标准和已知边界。

**现状观察**
列出相关文件、当前逻辑、数据流和重要约束。

**技术方案**
给出推荐方案，并说明为什么它适合当前代码库。如果存在多个可行方案，简要对比后明确推荐一个。

**改动预案**
- `path/to/file-a.ts`：改什么，为什么改
- `path/to/file-b.ts`：改什么，为什么改

**代码对比预览**
按文件展示关键 before / after 片段，只展示理解改动所需的代码。

**风险与验证**
说明潜在风险、兼容性影响、需要运行的测试和手动验证步骤。

**需要确认**
只提出真正阻塞实现的问题。如果没有阻塞项，说明可以继续进入实现。
```

## 代码对比规范

代码对比要服务于阅读体验，不要大段粘贴完整文件。优先展示最小必要片段。

每个文件建议使用下面的格式：

````markdown
### `path/to/file.ts`

修改原因：
说明为什么需要改这个文件。

修改前：

```ts
// 当前相关代码
```

修改后：

```ts
// 建议修改后的代码
```

影响：
说明改动后行为会发生什么变化。
````

如果改动较大，可以用摘要说明未展示的部分，只贴核心片段。除非文件很小或用户明确要求，不要整文件展示。

## 决策规则

- 不要在没有阅读代码的情况下直接给最终方案。
- 不要为了需求实现顺手做大范围重构。
- 不要新增抽象，除非它能明显降低复杂度，或符合项目已有模式。
- 优先使用项目中已有的工具函数、组件、状态管理方式、接口风格和测试习惯。
- 如果不需要改代码，要说明原因，并给出配置、文档、产品流程或使用方式上的建议。
- 如果有多个方案，简要比较成本、风险和扩展性，然后推荐一个。
- 如果需求不清晰，只问最少的阻塞问题。
- 如果涉及安全、权限、账单、隐私、数据迁移、破坏性操作或 API 兼容性，必须在实现前明确标出风险。
- 如果用户已经明确要求直接实现，可以先给简短方案，再继续改代码。

## 确认规则

遇到以下情况，实施前需要让用户确认：

- 产品行为存在歧义
- 多种 UX 或业务结果都合理
- 可能需要数据迁移
- 可能破坏 API 兼容性
- 涉及安全、权限、账单、隐私或破坏性操作
- 用户明确要求“先确认再修改”

不要过度提问。如果实现方向清晰且风险低，可以说明自己的假设，并在用户已经要求实现时继续推进。

## 范围控制

将改动分为四类：

- **必须修改**：满足产品需求所必需的改动。
- **建议修改**：能明显降低风险，或更符合当前架构的改动。
- **可选优化**：有价值但不是本次需求必需的清理或增强。
- **避免修改**：看起来相关，但会扩大范围或偏离需求的改动。

除非和需求实现强相关，否则不要把无关重构纳入方案。

## 复杂度分级

小改动的方案保持简短：

- 需求理解
- 涉及文件
- 关键 before / after
- 验证方式

中等改动需要补充：

- 当前数据流
- 实现顺序
- 风险和回退说明
- 重点测试

大型改动需要补充：

- 分阶段实现方案
- 数据迁移或兼容策略
- 测试矩阵
- 发布、灰度或回滚建议

## 验证要求

每个方案都必须包含验证计划。优先使用项目已有测试命令和验证习惯。

验证计划应包含：

- 需要运行的自动化测试
- 相关类型检查或 lint
- 用户可见行为的手动 QA 步骤
- 边界场景
- 如果本地无法完整验证，需要说明剩余风险

## 语言和风格

- 用户使用中文时，默认用中文回答。
- 文件路径、命令、代码标识符和 API 名称保持原文。
- 输出要便于阅读，不要堆砌架构术语。
- 重点是帮助用户快速判断方案是否靠谱，而不是制造流程负担。
- 对比代码要少而准，让用户一眼看懂变化。
