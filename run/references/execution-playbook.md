# Execution Playbook

## 开工前

先确认本次执行边界：

- 方案来源：来自当前对话、`plan` 输出、设计文档，还是用户口头描述。
- 必须修改项：本次一定要完成的行为或代码变化。
- 不做事项：方案中明确排除、建议但未确认、或会扩大范围的内容。
- 验证要求：方案要求的测试、lint、类型检查、脚本或手动 QA。

如果这些信息不足以安全开工，先追问或回到 `plan`。

## 实现顺序

推荐按下面顺序执行：

1. 读取方案涉及的代码、配置和测试文件。
2. 确认当前实现与方案描述是否一致。
3. 先改核心行为，再改外围接入。
4. 涉及 Java 代码新增或更新时，同步补齐类、方法、DTO/VO/Entity 属性和核心逻辑注释。
5. 补齐必要测试、示例或验证资产。
6. 运行最贴近改动的验证命令。
7. 读取最近编辑文件的 linter 诊断。
8. 根据验证结果修正实现。

不要为了追求一步到位，在没有检查当前代码的情况下大范围编辑。

## 偏差处理

遇到以下情况，必须显式说明偏差：

- 方案中的文件、函数或数据流已经不存在。
- 方案建议的实现会破坏现有接口或用户行为。
- 实现成本明显高于方案预期。
- 项目已有更合适的模式，与方案描述不同。
- 测试或 lint 暴露出方案未覆盖的约束。

偏差说明应包含：

- 原方案期待什么。
- 实际发现了什么。
- 调整后的做法是什么。
- 调整会带来什么影响。
- 如何验证调整后的行为。

## 验证策略

优先级从高到低：

1. 项目已有、最贴近改动的自动化测试。
2. 相关 lint、类型检查、编译或格式检查。
3. 针对改动路径的小脚本或命令。
4. 用户可见行为的手动 QA 步骤。
5. 无法执行时，说明原因和剩余风险。

如果验证命令耗时较长，可以先运行最小相关集合，再在最终回复中说明未运行的全量验证。

## Java 注释要求

当本次执行涉及 Java 代码的新增或更新时，必须按下面规则检查：

- 新增或更新的 Java 类需要有类级注释，说明职责或业务语义。
- 新增或更新的方法需要有方法注释，说明用途、关键参数、返回值或重要副作用。
- service 接口方法存在注释时，对应实现类方法也需要有方法注释，保持接口语义和实现说明一致。
- DTO、VO、Entity 的新增或更新属性需要有字段注释，说明字段含义。
- 核心业务逻辑、关键分支、兼容性处理和不直观的约束需要有简短意图注释。
- 注释内容必须言简意赅，只解释业务意图、字段含义、关键约束和必要背景。
- 避免无效注释：不要复述代码语法、方法名或显而易见的赋值流程，不为简单 getter/setter 或自解释代码添加噪音注释，除非项目规范要求。

## 工作区保护

- 开始前注意当前工作区可能已有用户改动。
- 不使用破坏性 git 命令。
- 不回滚 unrelated 文件。
- 如果必须编辑已有用户改动的文件，先理解现状，尽量只改本任务相关片段。
- 生成文件、格式化和批量替换要谨慎，避免制造无关 diff。

## 任务完成标准

只有同时满足以下条件，才算完成：

- 方案中的必须项已经落地。
- 代码行为和方案目标一致，或偏差已说明。
- 验证已执行到当前环境允许的程度。
- 新增或修改的复杂逻辑具备必要意图说明；涉及 Java 改动时，类、方法、DTO/VO/Entity 属性和核心逻辑注释已补齐，service 接口方法已有注释时对应实现类方法也已补齐注释，且注释简洁有效。
- 最终回复清楚列出完成内容、验证结果和剩余风险。
