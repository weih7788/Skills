# Execution Playbook

## 开工前

先确认本次执行边界：

- 方案来源：来自当前对话、`plan` 输出、设计文档，还是用户口头描述。
- 必须修改项：本次一定要完成的行为或代码变化。
- 不做事项：方案中明确排除、建议但未确认、或会扩大范围的内容。
- 验证要求：方案要求的测试、lint、类型检查、脚本或手动 QA。

如果这些信息不足以安全开工，先追问或回到 `plan`。

## 实现顺序

推荐按下面顺序执行：

1. 读取方案涉及的代码、配置和测试文件。
2. 确认当前实现与方案描述是否一致。
3. 先改核心行为，再改外围接入。
4. 补齐必要测试、示例或验证资产。
5. 运行最贴近改动的验证命令。
6. 读取最近编辑文件的 linter 诊断。
7. 根据验证结果修正实现。

不要为了追求一步到位，在没有检查当前代码的情况下大范围编辑。

## 偏差处理

遇到以下情况，必须显式说明偏差：

- 方案中的文件、函数或数据流已经不存在。
- 方案建议的实现会破坏现有接口或用户行为。
- 实现成本明显高于方案预期。
- 项目已有更合适的模式，与方案描述不同。
- 测试或 lint 暴露出方案未覆盖的约束。

偏差说明应包含：

- 原方案期待什么。
- 实际发现了什么。
- 调整后的做法是什么。
- 调整会带来什么影响。
- 如何验证调整后的行为。

## 验证策略

优先级从高到低：

1. 项目已有、最贴近改动的自动化测试。
2. 相关 lint、类型检查、编译或格式检查。
3. 针对改动路径的小脚本或命令。
4. 用户可见行为的手动 QA 步骤。
5. 无法执行时，说明原因和剩余风险。

如果验证命令耗时较长，可以先运行最小相关集合，再在最终回复中说明未运行的全量验证。

## 工作区保护

- 开始前注意当前工作区可能已有用户改动。
- 不使用破坏性 git 命令。
- 不回滚 unrelated 文件。
- 如果必须编辑已有用户改动的文件，先理解现状，尽量只改本任务相关片段。
- 生成文件、格式化和批量替换要谨慎，避免制造无关 diff。

## 任务完成标准

只有同时满足以下条件，才算完成：

- 方案中的必须项已经落地。
- 代码行为和方案目标一致，或偏差已说明。
- 验证已执行到当前环境允许的程度。
- 新增或修改的复杂逻辑具备必要意图说明。
- 最终回复清楚列出完成内容、验证结果和剩余风险。
