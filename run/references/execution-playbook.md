# Execution Playbook

## 开工前

先确认本次执行边界：

- 方案来源：来自当前对话、`plan` 输出、设计文档，还是用户口头描述。
- 必须修改项：本次一定要完成的行为或代码变化。
- 不做事项：方案中明确排除、建议但未确认、或会扩大范围的内容。
- 验证要求：方案要求的测试、lint、类型检查、脚本或手动 QA。

如果这些信息不足以安全开工，先追问或回到 `plan`。

## 实现顺序

推荐按下面顺序执行：

1. 读取方案涉及的代码、配置和测试文件。
2. 确认当前实现与方案描述是否一致。
3. 先改核心行为，再改外围接入。
4. 涉及核心业务逻辑、关键分支、兼容性处理、非直观约束或复杂算法时，同步补齐核心注释。
5. 涉及 Java 代码新增或更新时，同步补齐类、方法、DTO/VO/Entity 属性、Controller 接口和核心逻辑注释；类、方法、属性和 Controller 接口必须使用标准多行 JavaDoc，将 `/**`、正文、`*/` 分行书写，DTO、VO 的每个字段及 Controller 的每个接口都必须有注释。
6. 涉及上下文 UI 图生成时，按原上下文一比一完全复刻页面结构、组件、状态、间距、色彩、字号、文案和数据展示；不得自行改造成新的视觉风格。
7. 涉及 MyBatis Mapper 新增或修改时，将 SQL、动态条件和脚本放入对应的 Mapper XML，Java Mapper 接口只保留方法签名及必要的非 SQL 注解。
8. 补齐必要测试、示例或验证资产。
9. 运行最贴近改动的验证命令。
10. 读取最近编辑文件的 linter 诊断。
11. 根据验证结果修正实现。

不要为了追求一步到位，在没有检查当前代码的情况下大范围编辑。

## 偏差处理

遇到以下情况，必须显式说明偏差：

- 方案中的文件、函数或数据流已经不存在。
- 方案建议的实现会破坏现有接口或用户行为。
- 实现成本明显高于方案预期。
- 项目已有更合适的模式，与方案描述不同。
- 测试或 lint 暴露出方案未覆盖的约束。

偏差说明应包含：

- 原方案期待什么。
- 实际发现了什么。
- 调整后的做法是什么。
- 调整会带来什么影响。
- 如何验证调整后的行为。

## 验证策略

优先级从高到低：

1. 项目已有、最贴近改动的自动化测试。
2. 相关 lint、类型检查、编译或格式检查。
3. 针对改动路径的小脚本或命令。
4. 用户可见行为的手动 QA 步骤。
5. 无法执行时，说明原因和剩余风险。

如果验证命令耗时较长，可以先运行最小相关集合，再在最终回复中说明未运行的全量验证。

## 核心注释要求

当本次执行涉及代码的新增或更新时，必须按下面规则检查核心注释：

- 核心业务逻辑、关键分支、兼容性处理、非直观约束和复杂算法必须有简短意图注释。
- 注释内容必须言简意赅，只解释业务意图、关键约束和必要背景。
- 避免无效注释：不要复述代码语法、方法名或显而易见的赋值流程，不为自解释代码添加噪音注释。

## Java 注释要求

当本次执行涉及 Java 代码的新增或更新时，必须按下面规则检查：

- 类、方法、属性和 Controller 接口必须使用标准多行 JavaDoc：`/**` 独占首行，描述和每个标签各写在以 ` *` 开头的独立行，`*/` 独占末行。禁止 `/** 描述。 */` 或把描述、`@param`、`@return` 写在同一行；不得使用 `//`、普通块注释 `/* ... */` 或 Swagger 注解代替 JavaDoc。
- 新增或更新的 Java 类需要有类级注释，说明职责或业务语义。
- 新增或更新的方法需要有方法注释，说明用途、关键参数、返回值或重要副作用。
- service 接口方法存在注释时，对应实现类方法也需要有方法注释，保持接口语义和实现说明一致。
- DTO、VO 的每个字段都需要有字段注释，说明字段含义；Entity 的新增或更新属性也需要有字段注释。
- Controller 的每个接口都需要有接口注释，说明接口用途及必要的业务约束；按实际方法签名为每个参数添加 `@param`，为非 `void` 返回值添加 `@return`，为声明或需要说明的异常添加 `@throws`。
- 核心业务逻辑、关键分支、兼容性处理和不直观的约束需要有简短意图注释。
- 注释内容必须言简意赅，只解释业务意图、字段含义、关键约束和必要背景。
- 避免无效注释：不要复述代码语法、方法名或显而易见的赋值流程，不为简单 getter/setter 或自解释代码添加噪音注释，除非项目规范要求。

属性和方法注释示例：

```java
/**
 * 联系人姓名。
 */
private String contactName;

/**
 * 查询当前用户的联系人配置。
 *
 * @param id 配置 ID
 * @return 联系人配置
 */
public BookingContactConfigVO detail(Integer id) {
    // ...
}
```

Controller 接口注释示例：

```java
/**
 * 下载相关方 Excel 导入模板。
 *
 * @param response HTTP 响应，用于输出模板文件流
 * @throws Exception 模板读取或响应输出失败
 */
```

## MyBatis Mapper 要求

当本次执行涉及 MyBatis Mapper 的新增、生成或修改时，必须按下面规则检查：

- SQL 必须定义在对应的 Mapper XML 中，包含静态 SQL、动态条件、批量语句和 `<script>` 内容。
- Java Mapper 接口不得使用 `@Select`、`@Insert`、`@Update`、`@Delete` 等注解直接承载 SQL 语句或 SQL 片段。
- Mapper 接口只保留方法签名，以及 `@Param`、`@Mapper` 等不承载 SQL 的必要注解。
- 交付前检查新增或修改的 Mapper 接口及 XML，确认方法声明与 XML 的 `namespace`、语句 `id`、参数和结果映射一致。

## 工作区保护

- 开始前注意当前工作区可能已有用户改动。
- 不使用破坏性 git 命令。
- 不回滚 unrelated 文件。
- 如果必须编辑已有用户改动的文件，先理解现状，尽量只改本任务相关片段。
- 生成文件、格式化和批量替换要谨慎，避免制造无关 diff。

## 任务完成标准

只有同时满足以下条件，才算完成：

- 方案中的必须项已经落地。
- 代码行为和方案目标一致，或偏差已说明。
- 验证已执行到当前环境允许的程度。
- 新增或修改的核心业务逻辑、关键分支、兼容性处理、非直观约束和复杂算法已补齐简洁有效的核心注释。
- 涉及 Java 改动时，类、方法、DTO/VO/Entity 属性、Controller 接口和核心逻辑注释已补齐；类、方法、属性和 Controller 接口的 JavaDoc 均将 `/**`、正文、`*/` 分行书写，没有单行注释；Controller 接口已按实际签名补齐 `@param`、`@return`、`@throws`；service 接口方法已有注释时对应实现类方法也已补齐注释，且注释简洁有效。
- 涉及 MyBatis Mapper 新增或修改时，SQL 已全部放入 Mapper XML，Java Mapper 接口中不存在 `@Select`、`@Insert`、`@Update`、`@Delete` 等注解 SQL，且接口声明与 XML 映射一致。
- 涉及上下文 UI 图生成时，已按上下文一比一完全复刻；任何无法复刻或需要偏离的点均已先说明并获得用户确认。
- 最终回复清楚列出完成内容、验证结果和剩余风险。
