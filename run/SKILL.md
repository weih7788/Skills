# Run

## Role

这是方案落地实现的入口 skill，也是**执行闭环**的拥有者。

它只负责三件事：

1. 接收 `plan` 或用户提供的方案基线，并确认本次要实施的范围
2. 按方案修改代码、补齐必要测试或验证资产，并保持改动可追踪
3. 在最终交付时说明已完成内容、验证结果、偏离方案的原因和剩余风险

这个 skill 默认承接一个已经相对完整的方案。如果没有方案，或需求仍处于多方案取舍阶段，应先使用 `plan`。

## 底线规则

以下规则不可违反，没有灰度：

1. **没有方案基线不盲目开工**。如果用户没有提供方案，且需求不是轻量明确改动，先回到 `plan` 或追问最少的阻塞信息。
2. **不静默偏离方案**。实现中发现原方案不可行、成本过高或会破坏既有约束时，必须说明偏差、原因和调整后的做法。
3. **不把验证留在口头上**。能运行的测试、lint、类型检查或脚本要实际执行；不能执行时说明原因和剩余风险。
4. **不顺手扩大范围**。只实现方案中明确的必须项；建议项和可选项除非用户确认，否则不默认落地。
5. **保护用户已有改动**。遇到工作区已有变更时，先区分是否相关；不得回滚或覆盖用户未要求处理的改动。
6. **核心注释必须要有**。新增或修改代码时，核心业务逻辑、关键分支、兼容性处理、非直观约束和复杂算法必须同步补充简短意图注释，说明业务语义、关键约束和必要背景；不得留下无说明的核心逻辑，也不得堆砌复述代码的无效注释。
7. **Java 注释必须补齐且有效**。如果新增或更新 Java 类、方法、DTO、VO、Entity 或核心逻辑，必须同步补充言简意赅的必要注释；service 接口方法已有注释时，对应实现类方法也必须补充注释；不得留下无注释的新类、新方法、数据字段或复杂业务分支，也不得堆砌复述代码的无效注释。
8. **上下文 UI 图必须一比一复刻**。如果本次执行涉及根据上下文、截图、设计稿或既有页面生成 UI 图、交互图、效果图或 mockup，必须以原上下文为准进行一比一完全复刻，不得自行改配色、布局、组件形态、视觉密度、文案或交互状态；确需偏离时必须先说明原因并获得用户确认。

## 输入约定

- 用户通常会提供 `plan` 产出的方案、设计文档路径、任务清单、口头实现要求，或直接说“按方案实现 / run”。
- 如果方案来自当前对话上下文，先简要复述本次要落地的关键改动和不做的内容。
- 如果方案来自文件或文档路径，先读取该文件，再开始实现。
- 如果方案缺少关键约束，但改动很小，可以说明假设后继续；如果影响中等及以上，先追问或回到 `plan`。

## 工作模式选择

收到任务后，先判断是 `轻量执行`、`方案执行` 还是 `回到方案`。

### 轻量执行

满足全部条件时，可以直接实现：

- 用户目标明确
- 影响范围很小，通常不超过 1-2 个文件
- 不涉及新数据模型、协议、权限、安全、迁移或发布链路
- 不需要重新比较多种方案

处理方式：

- 简短说明实施假设
- 修改代码
- 做最小验证
- 汇报改动和验证结果

### 方案执行

出现以下任一条件，按方案执行：

- 用户要求“按方案实现”“继续实现”“run”
- 已存在 `plan` 输出、设计文档或任务清单
- 改动跨多个文件、模块或验证步骤
- 需要按既定范围逐项落地和回报

处理方式：

- 读取并确认方案基线
- 将方案拆成可执行步骤，必要时维护 todo
- 按步骤修改代码，保持每次编辑聚焦
- 每完成关键步骤后做局部检查
- 执行方案要求的验证，并补充实际验证结果

### 回到方案

出现以下任一条件，不直接继续实现：

- 需求目标不清晰，且实现会影响较大范围
- 方案中存在互相冲突的约束
- 实现中发现原方案会破坏兼容性、数据安全或核心业务规则
- 用户要求先评审或重新规划

处理方式：

- 停止扩大代码改动
- 说明当前发现的冲突或风险
- 给出调整方案或需要用户确认的问题

## 核心工作原则

1. **方案是执行合同**：默认按方案实施，不任意替换技术路线。
2. **小步修改，小步验证**：复杂实现按阶段落地，每个阶段尽量有可检查结果。
3. **项目约定优先**：复用现有目录结构、命名、框架、工具函数、测试方式和错误处理风格。
4. **行为可验证**：交付时不只说“已修改”，还要说明用户关心的行为如何被验证。
5. **偏差要可追溯**：任何偏离方案的实现都要能解释原因、影响和验证方式。
6. **最少惊扰工作区**：只改本次任务相关文件，不整理无关格式、不移动无关代码。
7. **核心注释随改动同行**：涉及核心业务逻辑、关键分支、兼容性处理、非直观约束或复杂算法的新增或修改时，必须补充简短意图注释；注释只写业务语义、关键约束和必要背景，避免重复代码字面含义。
8. **Java 注释随代码同行**：涉及 Java 代码新增或更新时，类和方法要添加简短说明性注释；DTO、VO、Entity 的属性要添加字段含义注释；service 接口方法存在注释时，对应实现类方法也要添加注释；核心业务逻辑、关键分支和不直观的约束要添加意图注释。注释只写业务语义、关键约束和必要背景，避免重复代码字面含义。
9. **UI 图按上下文逐项对齐**：涉及设计 UI 图生成时，逐项对齐上下文中的页面结构、组件、状态、间距、色彩、字号、文案和数据展示，目标是一比一完全复刻，而不是重新设计或风格化演绎。

## 执行流程

1. 确认方案基线：来源、目标、必须修改项、验证要求。
2. 检查当前代码：读取相关文件，确认方案仍匹配现状。
3. 拆分步骤：必要时使用 todo 跟踪实施、验证和收尾。
4. 执行改动：按项目风格编辑代码和测试。
5. 局部检查：读取 lints，运行可用测试或脚本。
6. 处理偏差：如需调整方案，先说明再继续。
7. 最终交付：说明完成内容、验证结果、未覆盖风险。

更细的执行约束见 [references/execution-playbook.md](references/execution-playbook.md)。

## 对外输出

最终输出应简洁说明：

- 实现了什么用户可见行为或工程能力
- 主要改动位置
- 实际执行过哪些验证
- 是否存在偏离方案、未验证项或剩余风险

具体格式见 [references/final-report.md](references/final-report.md)。

## 最终检查

交付前必须确认：

- 已按方案覆盖必须修改项
- 没有静默实现建议项或可选项
- 没有回滚、覆盖用户未要求处理的改动
- linter / 测试 / 脚本验证已尽量执行，并记录结果
- 新增或修改的核心业务逻辑、关键分支、兼容性处理、非直观约束和复杂算法均已补齐简洁有效的核心注释
- 涉及 Java 改动时，新增或更新的类、方法、DTO/VO/Entity 属性和核心逻辑均已补齐简洁有效的必要注释；service 接口方法已有注释时，对应实现类方法也已补齐注释
- 涉及上下文 UI 图生成时，已按原上下文一比一完全复刻，并明确记录任何已获确认的偏离点
- 偏离方案的地方已经说明原因和影响
- 最终回复能让用户判断下一步是否可以 review、测试或提交
