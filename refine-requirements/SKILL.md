# Refine Requirements

## Role

这是需求打磨和边界澄清的入口 skill。它用于把不完整、偏口头化或边界模糊的产品需求，整理成可评审、可进入后续方案设计的需求增强稿。

它只负责三件事：

1. 还原原始需求意图，并识别缺失信息、隐含假设和边界风险
2. 结合当前项目的代码、文档、接口、页面、数据模型或既有业务约定补齐需求细节
3. 输出增强后的需求说明、验收标准、影响范围、风险点和待确认问题

这个 skill 不负责技术方案设计、任务拆解或代码实现。需求打磨完成后，如用户要求设计方案，再交给 `plan`；如已有明确方案并要求落地，再交给 `run`。

## 底线规则

以下规则不可违反：

1. **不把猜测写成事实**。无法从需求或项目上下文确认的内容，必须标为“假设”或“待确认”。
2. **不擅自扩大产品范围**。可以提出建议和可选扩展，但必须和“本次必须范围”分开。
3. **先理解项目再补需求**。当用户要求结合当前项目时，必须读取相关代码、文档、接口或页面配置后再输出确定性补充。
4. **需求语言优先于技术实现**。输出重点是业务行为、用户流程、规则、边界和验收标准，不提前锁定具体实现方式。
5. **风险和冲突要前置**。发现与既有项目行为、权限模型、数据口径或外部系统约束冲突时，必须明确指出。
6. **金额类需求必须防资损**。只要涉及金额、余额、支付、计费、退款、结算、优惠、积分、额度、佣金、账单、发票或其他有资金/权益变动的场景，必须补齐安全设计、权限校验、幂等控制、并发控制、金额精度、账务一致性、审计追踪、异常补偿和对账验收，避免出现资损。
7. **不生成 UI 或交互设计图**。只要需求涉及新增页面、调整页面布局、修改组件、表单、弹窗、列表、详情、状态展示、交互流程或视觉层级，本 skill 只补齐页面入口、信息结构、字段规则、操作行为、状态反馈和验收口径；不询问用户是否生成图片，也不生成 UI 效果图、交互设计图、产品原型图或其他位图设计产物。
8. **问题要最少且高价值**。只提出真正影响需求定稿、方案设计或开发验收的问题，避免把所有不确定性都甩给用户。

## 输入约定

用户可能提供：

- 一段产品想法、PRD 摘要、用户故事、缺陷改进点或会议纪要
- 现有需求文档路径、截图、接口文档、页面地址或代码路径
- “帮我打磨需求”“补充下边界”“结合项目完善这个需求”等指令

如果用户没有给出项目位置，但当前工作区明显是相关项目，可以先从 README、知识库、路由、接口、数据库模型或近期文档中寻找上下文。若无法定位相关项目材料，先基于原始需求输出带假设的轻量增强稿，并列出需要补充的材料。

## 工作模式选择

收到任务后，先判断是 `轻量打磨`、`项目化打磨` 还是 `需求审查`。

### 轻量打磨

适用场景：

- 用户只提供一个早期想法或很短的需求描述
- 不要求结合代码或既有系统
- 目标是让需求更完整，便于继续讨论

处理方式：

- 复述需求目标和目标用户
- 补齐主流程、关键规则、异常场景和验收标准
- 标出本次范围、非本次范围、可选增强和待确认问题

### 项目化打磨

适用场景：

- 用户明确要求结合当前项目
- 需求会影响已有页面、接口、数据、权限、配置、通知、审批或外部系统
- 用户给出代码路径、文档路径、模块名、页面名或业务对象

处理方式：

1. 读取相关项目材料，还原当前业务现状。
2. 识别需求与现状的差异：新增行为、修改行为、兼容行为和废弃行为。
3. 补齐业务规则：角色权限、状态流转、数据口径、边界条件、异常处理、幂等/重复提交、审计日志、通知、导入导出、分页筛选、排序、搜索、国际化等。
4. 如涉及金额或权益变动，补齐资损防护要求：操作授权、金额来源、计算口径、精度与舍入、幂等键、重复提交、并发扣减、事务一致性、回滚补偿、对账、审计、风控限制、异常告警和人工处理入口。
5. 如涉及 UI 新增、调整或页面交互设计，补齐页面入口、布局结构、关键组件、字段展示、操作按钮、状态反馈、空态、加载态、错误态和响应式要求；不在本 skill 中生成 UI 效果图或交互设计图。
6. 补齐系统影响：页面、接口、数据表/字段、配置项、定时任务、消息队列、第三方集成、历史数据和发布兼容。
7. 输出可评审需求增强稿，并明确待产品确认的问题。

### 需求审查

适用场景：

- 用户提供一份已有 PRD、需求文档或用户故事，要求检查是否完整
- 用户关心边界遗漏、验收标准或可开发性

处理方式：

- 按风险优先列出缺失项和冲突项
- 给出推荐补充文本，便于直接合入原需求
- 输出完整增强稿或“审查问题 + 修改建议”，根据用户要求选择

## 打磨维度

按需检查以下维度，不必机械铺满：

- **业务目标**：解决什么问题，面向哪些用户，成功标准是什么。
- **用户与权限**：涉及哪些角色，不同角色能看、能做、不能做什么。
- **范围边界**：本次必须做什么，不做什么，哪些是后续可选。
- **核心流程**：入口、前置条件、主路径、结果反馈和退出路径。
- **状态与规则**：状态机、字段规则、计算口径、排序筛选、重复操作和并发场景。
- **异常场景**：无数据、失败、超时、权限不足、数据冲突、重复提交、部分成功、回滚或重试。
- **数据影响**：新增/修改/删除的数据，历史数据兼容，审计和追踪要求。
- **资金安全**：金额/权益变动的授权校验、幂等、并发、精度、账务一致性、异常补偿、对账、审计、告警和人工兜底。
- **页面与交互**：页面入口、列表/详情/表单行为、提示文案、空态、加载态、错误态、关键交互流程和响应式要求；涉及 UI 新增、调整或页面交互设计时，只输出文字化需求边界和验收口径，不生成 UI 效果图或交互设计图。
- **接口与集成**：调用方、被调用方、入参出参、错误码、外部系统约束和兼容性。
- **运营与配置**：开关、灰度、阈值、字典、模板、通知、导入导出和后台配置。
- **验收标准**：可测试的 Given/When/Then 或清晰场景清单。
- **风险与依赖**：跨团队依赖、数据迁移、权限安全、性能、合规、发布和回滚风险。

## 输出格式

默认输出一份可评审的需求增强稿。保持精炼，但要覆盖会影响开发和验收的关键边界。

如果用户要求输出“已经润色后的需求”“补充后的需求”“完整需求稿”“可直接贴进 PRD 的内容”等结果型内容，必须按照需求模板输出完整需求内容，且必须包含 **需求背景** 和 **需求分析** 两部分；不能只输出审查意见、零散补充点或问题清单。

推荐结构：

- **需求背景**：原始诉求、业务场景、目标用户、业务价值和本次要解决的问题。
- **需求分析**：现状依据、核心矛盾、影响范围、关键约束、假设和待确认的业务判断。
- **现状依据**：已阅读的项目材料、当前系统行为、重要约束。若未读取项目材料，说明原因和假设。
- **增强后的需求**：按功能点或用户流程描述必须范围。
- **边界与规则**：权限、状态、数据、异常、兼容和非本次范围。
- **安全与资损防护**：涉及金额或权益变动时必填；不涉及时可省略或说明“不涉及资金/权益变动”。
- **页面与交互需求**：涉及 UI 新增、调整或页面交互设计时必填，说明页面入口、页面结构、字段展示、操作行为、状态反馈、异常提示、空态/加载态/错误态和响应式要求；不涉及时可省略。
- **验收标准**：按场景列出可验证结果。
- **风险与依赖**：影响开发、测试、发布或产品决策的风险。
- **待确认问题**：少量高价值问题，按优先级排序。
- **可选扩展**：对当前需求有帮助但不建议默认纳入本次的增强项。

如果用户要求“可直接贴进 PRD”，输出更偏产品文档；如果用户要求“给开发看”，输出更偏开发可执行边界和验收口径。

本 skill 不负责生成 UI 效果图、交互设计图或产品原型图。若用户后续需要视觉方案、交互图或效果图，应在需求边界明确后交由对应的设计或方案流程处理。

## 与其他 Skill 的衔接

- 需求仍模糊、边界未定：继续使用 `refine-requirements`。
- 需求已经明确，需要技术方案、改动范围、风险评估或 before / after：交给 `plan`。
- 方案已经确认，需要实现、修复代码或验证闭环：交给 `run`。
- 需要审查已有方案或代码改动：交给 `review`。

## 最终检查

输出前必须确认：

- 已区分事实、假设和待确认项
- 已说明本次范围、非本次范围和可选扩展
- 已覆盖用户流程、规则边界、异常场景和验收标准
- 如果涉及金额或权益变动，已补齐安全设计、资损防护、对账审计和异常补偿验收；如果不涉及，已确认无需展开
- 如果涉及 UI 新增、调整或页面交互设计，已补齐页面与交互需求边界、状态反馈和验收口径，且未在本 skill 中生成 UI 效果图或交互设计图；如果不涉及，已确认无需展开
- 若要求结合项目，已经读取足够支撑结论的项目材料
- 没有提前进入技术方案或代码实现
- 当用户要求输出润色或补充后的需求正文时，已按需求模板输出，并包含需求背景和需求分析
- 待确认问题数量克制，且每个问题都会影响需求定稿或开发验收
