# Review 审查

使用该 skill 审查最近一次代码或方案修改是否存在明显 bug、潜在风险、遗漏验证或实现偏差。只做分析和建议，不擅自修改代码、方案或测试。

## 审查范围

- 优先审查用户明确指定的对象：粘贴的 diff、方案文本、文件路径、分支、提交、PR 或某个具名改动。
- 如果用户没有指定对象，按以下顺序定位最近相关修改：
  1. 当前对话上下文中的修改或方案。
  2. 当前 git 工作区的未提交改动。
  3. 当前 git 仓库的最新一次提交。
- 如果目标不明确且存在多组无关改动，先说明审查假设，再聚焦最可能符合用户意图的改动。
- 除非用户明确把请求从审查改为实现，否则不要执行代码修改、格式化、暂存、提交或清理操作。

## 工作流程

1. 确认审查对象。
   - 审查工作区时，优先使用 `git status --short`、`git diff --stat`、`git diff`，必要时查看 `git diff --staged`。
   - 审查最新提交时，使用 `git show --stat --oneline --decorate HEAD` 和聚焦后的 `git show` 输出。
   - 审查方案或文档时，阅读变更文本以及直接相关的上下文。
2. 先理解意图，再判断风险。
   - 从用户请求、提交信息、设计文本、测试、附近代码和命名中推断预期行为。
   - 阅读足够的周边代码，确认改动是否符合现有契约、调用链和项目模式。
3. 优先报告高价值问题。
   - 重点关注明确 bug、行为回归、数据一致性风险、安全/隐私风险、兼容性问题、并发/幂等风险、边界条件遗漏，以及会掩盖问题的验证缺口。
   - 避免只讨论风格偏好；除非风格问题会造成真实的维护或正确性风险。
4. 在成本低且不侵入的前提下验证判断。
   - 可以运行只读检查或现有测试来确认风险。
   - 不要为了复现问题而编辑文件。如果复现需要改动或额外搭建，描述建议的验证方式即可。
5. 输出审查结论。

## 输出格式

先列风险项，按严重程度排序，并尽量给出具体位置。

每个风险项包含：

- **风险**：简短标题，并标注严重级别，例如 `[P0]`、`[P1]`、`[P2]`、`[P3]`。
- **位置**：文件和行号、提交片段、方案章节或段落。
- **原因**：说明为什么会失败，以及触发条件是什么。
- **建议**：给出具体修复、缓解或验证建议。

风险项之后补充：

- **问题 / 假设**：仅在确有必要时列出。
- **审查总结**：简短说明审查了什么，以及是否存在未验证的残余风险。

如果没有发现问题，要明确说明“未发现明显问题”，并补充未执行的验证或仍然存在的不确定性。

## 严重级别

- `P0`：数据丢失、安全漏洞、生产故障，或改动完全不可用。
- `P1`：高概率用户可见 bug、核心流程中断、严重兼容性或迁移风险。
- `P2`：边界场景 bug、有实际影响的可维护性风险、重要验证缺失。
- `P3`：轻微正确性、清晰度或未来演进风险，值得提示但通常不阻塞。

## 约束

- 不要静默修改被审查的代码、方案、文档或测试。
- 不要过度审查无关的历史代码；只有当最近改动新暴露或依赖这些问题时才提及。
- 如果用户只说“review”但没有更多说明，默认采用代码审查立场：风险项优先，简短总结随后。
- 如果证据不足，将结论标记为“疑问”或“风险关注”，不要包装成已确认 bug。
